# Bilingual (i18n) setup — approach and reuse notes

A working pattern for making a small front-end project bilingual in English and
Chinese. Written so it can be lifted into the next project rather than
re-derived: copy `js/i18n.js`, the two locale files, and the three checks at the
bottom of this document.

## What this project does

- Interface and documentation are bilingual; **code is English only** —
  comments, test names, assertion messages. The repository therefore reads as an
  English project with a localised interface, which is the convention
  open-source projects expect, while Chinese users get a fully Chinese UI.
- The language follows the browser on first run and remembers an explicit
  choice afterwards.
- Practice *content* (code lines, symbol tokens) is not translated: code is
  code, and both audiences drill the same material. Only labels, descriptions
  and messages are localised.

## Decision 1 — dictionaries are inlined as classic scripts, not JSON

**Dictionaries must be JavaScript files, never JSON loaded by `fetch`.**

If a page is opened directly from disk (`file://`), the browser refuses to
`fetch` or `XHR` a local file for CORS reasons. A JSON dictionary therefore
fails exactly in the "double-click it and it works" scenario that makes a small
tool pleasant to use — the page loads, then renders nothing useful because no
translations arrived.

The same constraint applies to ES modules: `<script type="module">` is also
blocked under `file://`. So the whole project uses classic scripts, and
`index.html`'s script order is its dependency order. `i18n.js` must load before
any module that reads a translation, and the dictionaries before the first
render.

## Decision 2 — resolve strings at call time, never at load time

This is the single most common way a hand-rolled i18n layer half-works: the
language switch only affects the parts of the page that happen to re-render.

```js
// WRONG — frozen at load; a language switch will not change it
var FINGERS = { L5: { label: t('finger.L5') } };

// RIGHT — translated on every read
var FINGERS = { L5: {} };
Object.defineProperty(FINGERS.L5, 'label', {
  get: function () { return t('finger.L5'); }
});
```

The accessor form is worth preferring over rewriting every call site: existing
code that reads `FINGERS[id].label` keeps working, and it becomes late-bound for
free. Make the accessors non-enumerable so `Object.keys()` and JSON round-trips
stay predictable.

Anything derived at load time from a translated value is a bug for the same
reason: character names, group labels, generated drill titles. Build those
inside the function that returns them.

## Decision 3 — the runtime API

`js/i18n.js` is deliberately small (~250 lines) and has no dependency on
storage, so it is testable in isolation. The pieces that matter:

| Function | Purpose |
|---|---|
| `addDict(lang, dict)` | called by each locale file at load; merging is allowed |
| `t(key, params)` | lookup + `{name}` interpolation + `{one, other}` plurals |
| `tryT(key, params)` | same, but `null` instead of the key when missing |
| `resolve(setting)` | turns `'auto'` into a concrete language via `navigator.language` |
| `set(value)` | switches, updates `<html lang>` and `<title>`, notifies listeners |
| `init({ setting, persist })` | wiring injected from boot, so the module stays storage-free |
| `applyDom(root)` | translates static markup via `data-i18n` / `-title` / `-placeholder` / `-aria` |
| `missingKeys()` | records every key that failed to resolve, for diagnostics and tests |
| `joinList(items)` | locale-appropriate list separator (Chinese uses `、`, English `, `) |

A missing key returns **the key itself**, not `undefined`. A raw key name on
screen is immediately recognisable and debuggable; `undefined` is not.

Values may be a string or `{ one, other }`. Chinese has no grammatical number, so
its dictionary simply uses a plain string for the same key — the parity check
compares keys, not value shapes.

### Key naming

Flat dot-notation namespaces, with the prefix identifying the owning area:
`nav.practice`, `settings.theme.auto`, `practice.hud.cpm`, `kind.missing-shift`.
A translator must be able to guess where a string belongs from its key alone.

### Language names stay in their own script

In *both* dictionaries the Chinese name is written in its own script:
`'lang.name.zh-CN': '中文'` <!-- i18n-check-allow: quoted dictionary value -->
so a user looking for their own language recognises it without reading the
current interface language.

## Decision 4 — three checks that keep it honest

These are what turn "we translate as we go" into something that cannot silently
rot. All three live in the Node test runner.

**1. Dictionary key parity.** Both dictionaries must contain exactly the same
keys. A half-translated release fails the suite instead of quietly falling back
to English for the missing half.

**2. Every key referenced from source exists.** Scan the source for `t('…')` /
`tr('…')` / `labelKey: '…'` call sites and verify each dotted literal against the
dictionary. Strip comments first, or documentation examples get counted as real
references.

**3. No CJK outside the locale directory.** One rule that catches both
untranslated interface strings and untranslated comments:

```js
var CJK = /[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]/;
```

This has the useful side effect of forcing comments to be translated too, which
is what keeps a bilingual repository readable to everyone.

A line may opt out with an explicit marker — for the rare case where a test
legitimately asserts on a Chinese dictionary value:

```js
t.eq(I.t('nav.practice'), '练习', 'a Chinese lookup should resolve'); // i18n-check-allow
```

Prefer an explicit per-line marker over excluding a whole directory: the
decision stays visible and reviewable.

**4. Families built by concatenation need their own case.** The static scan
cannot see `t('stats.overview.' + id + 'Sub')`. Enumerate those families in a
test and check every member in every language:

```js
[['stats.overview.', ['sessions', 'chars', 'avgCpm']], …].forEach(function (fam) {
  fam[1].forEach(function (m) {
    var key = fam[0] + m;
    langs.forEach(function (l) {
      t.ok(I.keysOf(l).indexOf(key) !== -1, '[' + l + '] missing ' + key);
    });
  });
});
```

In this project that case immediately found four statistics sub-labels that were
referenced but never defined — the raw key names were being rendered into the
interface in both languages. Parities and reference checks alone would not have
caught it.

## Recipe for the next project

1. Copy `js/i18n.js`, `js/locales/en.js`, `js/locales/zh-CN.js`, and the language
   row from the settings view plus the top-bar switch.
2. Load `i18n.js` first, then the dictionaries, then everything else — as
   classic scripts, so `file://` keeps working.
3. In boot: `I18n.init({ setting: <stored or 'auto'>, persist: fn })`, then
   `I18n.set()` on change and re-render the current view in the listener.
   Remember to relabel any long-lived objects that are reused across renders
   (in this project, the on-screen keyboard updates its legends and tooltips).
4. Put the pre-paint language decision in a small inline `<head>` script, so the
   document language is right before first paint — the same trick used for the
   theme.
5. Port the three checks; add a family case for every concatenated key.
6. Write the README twice, cross-linked at the top of both. **Whichever language
   you want the repository to show by default must be `README.md`** — that is the
   only filename GitHub renders on the landing page. The other language lives
   beside it (`README.en.md` here, or `README.zh-CN.md` if the default is
   English). Exclude the default one from the "no CJK outside locales" check;
   the checked file is the non-default one.

## Pitfalls met in this project

- **CSS `content:` cannot be translated.** A pause overlay whose text lived in
  `content:` had to become a real element. Any user-visible text must exist in
  the DOM. <!-- i18n-check-allow: the quoted example is the point of the pitfall -->
- **Plurals change string length, which changes layout.** English labels are
  often longer than Chinese; rows that fit on one line in one language wrap in
  the other. Use `flex-wrap` and check both languages.
- **`tryT` returning `null` is the right tool when a string is genuinely
  optional.** Making a metric's sub-label optional fixed the missing-key bug
  above without inventing four empty dictionary entries.
- **Keep the fallback language explicit.** English is the fallback here, because
  it is the repository's primary language. Detection defaults to it when the
  browser language is neither supported value.
